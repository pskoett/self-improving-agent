# Feature Requests

Capabilities requested by user that don't currently exist.

## Entry Template

Copy and fill in this entry. The request remains historical fact even if needs or capabilities change. Maintain any reusable inference (for example, that an API lacks an endpoint), not the user's preference itself.

```markdown
## [FEAT-YYYYMMDD-XXX] capability_name

**Logged**: ISO-8601 timestamp
**Priority**: medium
**Status**: pending
**Area**: frontend | backend | infra | tests | docs | config

### Requested Capability
What the user wanted to do

### User Context
Why they needed it, what problem they are solving

### Complexity Estimate
simple | medium | complex

### Suggested Implementation
How this could be built, what it might extend

### Metadata
- Frequency: first_time | recurring
- Related Features: existing_feature_name
- Pattern-Key: area.symptom (optional; usually dedupe by capability)

### Maintenance
- Claim: unknown — identify any reusable inference during triage
- Scope: unknown
- Authority: unknown
- Decay: unknown / unknown
- Revalidate: before relying on the claim, establish scope/authority and choose the cause-specific check and trigger
- Validation: pending
- Evidence: none yet
- Disposition: retain — provisional, not validated
- Guidance: none

---
```

Use the skill's Maintenance instructions to record actual dated evidence and usefulness separately from truth. Missing/conflicting evidence stays unresolved. Never change preferences due to age/disuse; retain request and promotion history even when retiring obsolete guidance. Do not count reviews as repeated requests or bulk-migrate legacy entries.
